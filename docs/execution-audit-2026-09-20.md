## 2. 必须优先修复的发现

### A1：PDF 限制位于整文件读取之后，且会提前终止其他候选路径〔高〕

证据：`src/adapters/pdfExtractorPipeline.js:92` 在选择提取器前执行 `readFile(sourcePath)`；`src/adapters/pdfMarkdownConverter.js:451` 才检查 128 MiB 输入上限，随后又读取一次文件。直接调用无 converter 的流水线路径也没有执行该输入大小检查。`pdfExtractorPipeline.js:144` 直接重新抛出资源超限异常，`:164` 所在分支会让 auto、marker、scientific 先运行内置提取器。

影响：三本大书虽然返回 `PDF_INPUT_LIMIT`，此前已在流水线分配过整文件 Buffer；受支持大小的默认路径还会重复读取。不能声称“读取前拒绝、没有分配数百 MB”。该限制也可能在所选增强提取器运行前终止整个任务。解压字节预算不等于进程总内存上限，不能把快速拒绝大书当作大文档能力已经稳定。

修正方向：明确文件准入限制与各提取器预算的区别；在整文件分配之前完成准入检查；去掉重复读取，验证作业和直接入口行为一致。安全地停止过载路径是必要措施，但 128 MiB 只是当前实现限制，不是用户已接受的最终产品范围。支持这些大书应依赖有界的真实页面后端，不能只放大上限。

### A2：作业入口丢失预算参数，64 MiB 压测配置没有生效〔高〕

证据：`src/core/documents.js:898` 附近的 `convertDocumentToMarkdownAsJob` 调用仅传递进度回调、页检查点回调、preferredExtractor 和 force，未传 `maxDecompressedBytes`、`maxInputBytes`。内层 `:445` 才转发二者。作业检查点 options 也没有记录这些预算。

影响：上一轮 worker 经该入口指定的 64 MiB 解压预算会退回默认值；不能据此评价 64 MiB 配置下的耗时、资源限制或调参效果。`test/core-documents.test.js:633` 和 `:640` 只验证低层转换器，覆盖不到作业入口。

修正方向：让有效配置贯穿实际产品入口，并保存到任务证据；校验非有限数值、非法值与默认值。新增入口级用例，验证限制实际生效，而非只检查传参形状。

### A3：DOCX 图片路径被截断，去重可能合并不同图片〔高〕

证据：`src/adapters/docxMarkdownConverter.js:61` 输出 `![Word image](<路径>)`；`src/core/documents.js:475` 的目录保留文件名中的括号。`src/adapters/documentIr.js:73` 用 `[^)]+` 截取图片目标，并直接以结果为 Map 键和资产路径。

例如 `![Word image](<assets/高中物理竞赛讲义(完整版).docx/image1.png>)` 会被截成 `<assets/高中物理竞赛讲义(完整版`。同目录的 image2.png 会得到相同键；不含括号的目标也仍携带 `< >` 分隔符。

影响：新增去重解决了重复引用触发 ID 冲突的一类问题，却不能证明资产索引正确。上一轮 DOCX 有 363 个图片引用、IR 只有 2 个资产，截断可以解释这一异常，但原输出已删除，无法逐项确认。引用数不等于唯一图片数，也不能据此声称磁盘图片或原 Markdown 已丢失。现有非 PDF IR 测试只覆盖简单路径和同路径重复引用。

修正方向：解析完整 Markdown 图片目标，支持实际生成的尖括号、空格、括号及行内图片形式；保留同图多次引用，避免不同图片误合并。验证引用到文件的映射和可达性，不能只比较资产计数。

### A4：正文、结构索引与资产尚未按同一修订提交〔高〕

证据：`src/core/documents.js:580` 起在用户编辑分支写 refreshed 候选，`:615` 起在另一分支写当前正文；`:727` 和 `:765` 附近按新提取 Markdown 计算 IR 修订并更新同一组 documentIr 字段。IR 失败在 `:755`、`:784` 附近仅追加警告，旧 IR 指针不清除或标为过期。`src/core/appService.js:531` 读取当前 Markdown，`:556` 仅凭指针读取 IR 后用于交换包，没有核对两者属于同一修订。

此外，修订 ID 只含 Markdown 内容哈希；源文件、引擎、规则、选项或版面证据改变但正文不变时仍会落到同一 IR 目录。`src/core/documentIrStore.js:65` 逐页覆盖，`:87` 最后写索引，只保证单个 JSON 原子替换，不能保证整套修订原子提交。`documents.js:64` 附近还按新 visual map 删除不在新引用集内的旧视觉资产。

影响：新正文可能搭配旧 IR；保留用户编辑正文时可能搭配新候选 IR；旧正文仍引用的视觉资产也可能受新提取清理影响。当前不能称为“修订提交已完成”。这些是静态代码确认的条件风险，本轮没有运行写盘失败或编辑故障注入。

修正方向：当前版本、刷新候选分别持有正文/资产/结构/质量指针；完整候选通过校验后统一切换。失败保留旧整套结果，过期来源显式标记；交换包校验正文与结构的对应关系。缓存身份包含来源和有效处理版本/配置。

### A5：页覆盖率只统计已创建的页，漏页可以得到 100%〔高〕

证据：`src/core/conversionQuality.js:19` 以 `documentIr.pages.length` 为分母，`:37` 未对照 `documentIr.source.pageCount`。`src/adapters/pdfDocumentIr.js` 主要从 visual map 和正文页标记创建页，没有为源文档所有页面建立状态账本。

影响：若来源有 100 页而 IR 只含 1 个 completed 页，当前汇总仍得到 100% 覆盖；这是公式推导，不是本轮实测。上一轮五个 PDF 的 IR 页数均为 0，也无法证明完整性。TXT/DOCX 的一个逻辑部分不能作为一个真实物理页面计量。

修正方向：区分来源页总数、已处理页、缺失页及逻辑部分。来源页数未知时覆盖率应为 unknown，已知时所有源页必须有明确状态；空白页、失败页、仅保留原图的页分别记录。启发式置信度不等于识别准确率。

### A6：取消可能被旧清单覆盖，检查点尚不能恢复执行〔高〕

证据：`src/core/documents.js:312` 在长转换前读取 manifest，`:789` 附近将它整体写回；转换期间 `src/core/jobs.js:55` 在另一份 manifest 上保存取消状态。`src/core/manifest.js:116` 排队写入传入的快照，没有合并最新任务状态。后置 `assertNotCancelled` 因而可能读取到被覆盖后的 running 状态。取消只在转换边界检查，没有向提取器传递停止信号。

检查点的 `isCheckpointReusable` 在生产执行入口没有调用；PDF 页记录在整文档 IR 生成后补写，未附完整可复用页产物。保存了状态不等于能从断点恢复。

影响：用户取消后工作仍可能继续，输出可能已写入，甚至最终变回 succeeded。大文件超时依赖测试脚本杀进程，不能算产品具有可取消能力。

修正方向：先保证取消状态不被覆盖、提交前再次检查、旧结果不受影响；随后随页面 worker 建设停止信号、进程回收和可靠恢复。不要只改界面文字或检查点状态来宣布恢复能力完成。

## 4. 对今天执行方式的判断

应保留：DocumentIR 基础模型、非 PDF 逻辑部分、不伪造页码、质量信号、公式回归、资产引用去重的目标，以及大 TXT 索引优化。没有证据支持全面回滚或改写已确认正确的转换规则。

应停止的推进方式：按“又完成若干批次/新增若干文件”衡量质量提升；把适配现有 Markdown 称为真实页面后端；在没有基线和页面覆盖证据时继续增加结构规则；依靠限制大文件或删除测试产物收尾后宣布任务完成。

性能还有明确边界：写盘和 PDF 页映射已经改为按页索引，流扫描也改为单次定位 `stream` 标记，但写盘前仍会克隆全量 IR。非 PDF 大 TXT 变快不能证明多页 PDF 已无类似增长问题。后续应在真实页后端和有界存储链路上度量，不再通过堆叠正则规则承担通用 PDF 解析。

### B1：取消状态保存了，成果仍被覆盖〔P0；已复现〕

通过 `convertDocumentToMarkdownAsJob` 先生成旧正文，再在转换器返回前调用 `cancelJob`。最终作业确为 cancelled，但原正文被 NEW 替换，DocumentIR 修订也改变，文档状态为 ready。`src/core/documents.js:618`、`:619` 写正文，`:821` 保存文档清单；后置取消检查在 `:945` 才运行。非 PDF 转换器调用没有获得停止信号。`jobs.js` 的成功前检查因此保护不了已经写入的成果。

另一个复现把相同毫秒时间戳的 running 快照写回，已取消作业恢复为 running：`src/core/manifest.js:128` 仅按 updatedAt 严格大于合并，没有保证终态不可回退。静态检查还发现 PDF 内置提取的 catch 会吞掉 job_cancelled；若进入可选提取器，execFile 调用没有取消信号。后两项没有进行进程回收实测。

解决方案：以作业/文档串行提交点协调取消和成果切换；所有转换先写候选目录，检查取消与预期当前修订后再提交统一指针。提交与取消谁先获得提交权决定终态，禁止出现 cancelled 却提交成果的状态。取消向转换器和子进程传递；取消异常直接上传，不能进入降级候选。时间戳只用于展示，不能承担终态优先级。

### B2：当前正文与刷新候选仍混用，整套修订不是原子提交〔P0；部分已复现〕

编辑旧正文后重提取：`outputMarkdownPath` 保留编辑内容，而 `markdownOutputs.defaultForAi` 指向 refreshed 文件，`qualityReportId` 和 warnings 变成候选的值。当前/候选 IR 字段拆分是有效的局部改进，但 `src/core/documents.js:640–705` 的共享元数据仍无条件更新。

静态确认：PDF visual map 在 `documents.js:552` 提前写入固定资产目录，`:63` 可删除旧正文仍引用的图片；IR 写入失败仅警告/清指针，已写正文不回滚。`documentIrStore.js:59–98` 覆盖同一修订的页文件后才写 complete 索引，旧 complete 索引在中断时仍可能指向部分新页；未做磁盘故障注入，不能把这些风险写成已实测损坏。

修订 ID 当前包含源哈希、转换器版本、提取 Markdown；仍缺实际后端身份、有效配置、处理规则与版面/资产摘要。同正文、不同版面可写进同一目录。`appService.js:558–569` 会检测过期 IR，但 catch 静默丢弃结构；交换包选择最近 sourceRef evidence，尚未要求与当前修订匹配。

解决方案：当前与候选分别持有正文、readable、资产、IR、质量、证据整套指针；建立不可变修订目录，完成校验后一次切换。未引用旧资产的回收放到提交后，先核对仍在使用的修订。交换包要么使用完全一致的修订，要么明确标注结构缺失/过期，不能静默宣称结构有效。

### B3：图片索引仍漏记或误记〔P1；已复现〕

`src/adapters/documentIr.js:30` 的图片匹配锚定行首，`:107` 每行仅解析一次且未排除代码块。三项结果为：正文中一张图片索引为 0；同一行两张图片只索引第一张；围栏代码示例里的图片被当成真实资产。中文、空格、括号和尖括号的行首路径用例已通过，应保留。

解决方案：解析现有生成器实际使用的 Markdown 图片语法，记录每个引用位置和多资产关联；正确处理转义、标题、行内/多图、代码围栏与内联代码。按规范化目标去重，保留各引用关系，再核对真实资产文件，不能通过扩大一条行首正则结束任务。

### B4：覆盖率仍能虚报，页总数只是启发式〔P1；已复现〕

`conversionQuality.js:29` 仍在来源页数未知时回退到已生成页数。未知来源的 1 个 completed 页得到 coverage=1、clean_readable/high；非 PDF 逻辑部分也得到物理页覆盖率 1。2 页中 1 页 pending 仍被标 clean_readable；两个 pageNumber=1 的 completed 记录足以让 2 页文档报 100%。

`detectPdfPageCount` 对字典 `Type /Pages` 在 Count 之前返回 12，调换同一字典字段顺序就返回 null。当前正则不能作为权威页树解析器，也未验证压缩对象页树。解决方案：未知物理页数保持 null，逻辑部分单独计数；按唯一合法源页号建立账本，区分已处理覆盖率与内容完整性，pending/partial/failed 不得冒充已完整。启发式计数保留出处和可信级别，真实页总数由页面后端提供。

### B5：资源入口已改善，但还没有产品级资源保证〔P1；代码确认与小型复现〕

流水线现在确实先 stat 再分配整文件 Buffer，转换器也复用了 Buffer；这部分不应回滚。`assertPdfInputSize` 将非法字符串转为 NaN，Infinity 也被接受，200 MiB 的检查因此可绕过限制。解压预算存在同类数值归一问题，后者本轮未运行过载输入。

此外，作业启动检查点前仍完整流式读取源文件求哈希（`documents.js:907`）；导入阶段 `records.js:12` 更会 readFile 整文件求哈希。所以直接调用转换器得到的“0 ms 拒绝”不能外推为导入到转换全过程零读取或零大分配。现有可选后端也在统一入口先受整文件读取限制。解决方案：入口统一验证有限正整数预算；区分导入、指纹计算、准入和后端预算，采用流式指纹/有界读取，明确允许 fallback 的超限类型。三本大书仍须实际转换验收，不能只提高阈值。
